# 1. 目标

1. **完整字段级 IR（请求 + 非流式响应 + 流式）**：两个协议的已知特有字段与结构性信息都有具名类型定义。
2. **字段级 droppability**：策略类型绑定到 IR 类型，支持递归与值依赖，编译期强制覆盖。
3. **能力优先投影**：先判断目标能否**语义等价**表达或转换，只有确实无法等价时才进入 droppability 裁决。
4. **同协议无损往返**：`from === to` 也走完整 `parse → IR → render`，以「语义等价」为准（前提见 §4.4）。
5. **fail-closed**：不可丢弃字段无法投影时抛错；`drops` 记录真正丢弃的字段。
6. **保留 warning 聚合体系**：Privacy / Cache / 运行时诊断继续存在；仅「字段保真裁决」不再以 warning 表达。

> **DEC-4 边界：** 不删除 `TranslationWarning`/`Fidelity`/`ctx.warnings`。保真裁决改 drop/throw 后相关 warning 站点被移除；②③④ 继续进入统一聚合视图（`trace.warnings`）。`Fidelity` 计算见 §9.1。

| 编号 | 决策 |
|---|---|
| DEC-1 | **单一 IR + 协议命名空间 Native 分区**；协议字段用具名类型，不用 blob。 |

# 4. 保真定义与边界

## 4.1 三种「等价」

| 层级 | 定义 | 承诺 |
|---|---|---|
| **语义等价** | 业务语义一致（角色、顺序、内容、工具配对、停止原因、用量） | ✅ 同协议必须满足 |
| **结构等价** | JSON 结构逐字段一致（键顺序除外） | ⚠️ 已知字段尽力 |
| **SSE 帧等价** | ping、chunk 边界、帧顺序一致 | ❌ 不承诺 |

## 4.2 Presence 模型

- **缺失 vs 显式 `null`**：`undefined` 缺失；协议显式 `null` 以存在且为 `null` 表达。
- **空数组 vs 缺失**：可区分。
- **单值 vs 数组**：`native` 保留原始形态提示，render 优先原始形态。

## 4.3 round-trip 验收（双测试）

| 测试 | 验证性质 |
|---|---|
| `normalize(render(parse(x))) ≈ normalize(x)` | **原始输入未丢失**（对原始输入比较） |
| `parse(render(parse(x))) ≈ parse(x)` | 编解码稳定 |

`normalize` 仅处理键顺序与已声明 Presence 默认值，**不得**合并语义不同字段。

## 4.4 无损保证的前提（P1-3）

「同协议无损」**不是**对任意输入的绝对承诺，前提为：

1. 输入符合来源协议或其**已声明兼容方言**。
2. 输入通过协议验证与安全策略。
3. 未启用**改变语义**的 Feature Adaptation。
4. 目标协议可表达该输入；同协议未知字段仅在允许**不透明保留**（`opaque_native`/`extra`）时往返。

启用 Privacy 后，若未知 Native 动态键名无法登记，按 `reject`（fail-closed）——这是安全策略，**不违反** §4.3 的保真口径。

# 5. IR 结构设计

## 5.1 Native 容器与具名类型

```ts
interface NativeByFormat<A, C> {
  anthropic?: A;
  chat?: C;
}

type NativeRequest  = NativeByFormat<AnthropicNativeRequest,  ChatNativeRequest>;
type NativeMessage  = NativeByFormat<AnthropicNativeMessage,  ChatNativeMessage>;
type NativePart     = NativeByFormat<AnthropicNativePart,     ChatNativePart>;
type NativeTool     = NativeByFormat<AnthropicNativeTool,     ChatNativeTool>;
type NativeResponse = NativeByFormat<AnthropicNativeResponse, ChatNativeResponse>;
type NativeChoice   = NativeByFormat<AnthropicNativeChoice,   ChatNativeChoice>;
type NativeStream   = NativeByFormat<AnthropicNativeStream,   ChatNativeStream>;
```

- 每个 IR 节点只挂自身 `native` 类型（`CanonicalTool.native?: NativeTool`），协议+节点双重隔离。
- **`refusal` 归属（修 P0-5 双写）：** `refusal` 只由公共 `RefusalPart` 承载，`ChatNativeMessage` **不再**包含 `refusal`。
- **Chat 长度字段形态：** 请求保留原始形态提示 `ChatNativeRequest.maxTokensField?: "max_tokens" | "max_completion_tokens"`。
- 具体字段清单见 §13 的 Schema 文件；本正文不再用 `/* ... */` 示意。

## 5.2 消息序列、角色与 system

```ts
export type MessageRole = "system" | "developer" | "user" | "assistant" | "tool";
```

- `messages` 是序列事实来源；parse 不合并/搬移/丢弃。
- `CanonicalRequest.system` 移除；`native.<proto>.origin` 记录 system 来源位置。
- `native` 只保存来源位置**元数据**，不重复语义内容（§5.6）。

### 5.2.1 Role Projection 与 `RoleCapabilities`（P1-1 修正）

```ts
interface RoleCapabilities {
  /** 目标支持会话中途 system 消息。 */
  midConversationSystem?: boolean;
  /** 目标支持 developer 角色（与 system 各自独立）。 */
  developerRole?: boolean;
  /** 目标支持 system 消息的 clear_at。 */
  systemClearAt?: boolean;
  /** 目标支持逐消息 output_config。 */
  perMessageOutputConfig?: boolean;
}
```

| 源角色 / 位置 | 目标 anthropic-messages | 目标 openai-chat |
|---|---|---|
| system（首部连续段） | 提升为顶层 `system`（语义等价） | `system` message 原位 |
| system（会话中途） | `RoleCapabilities.midConversationSystem` 为真 → 原位；否则 `required` 抛错 | 原位 |
| developer | `RoleCapabilities.developerRole` 为真 → 原位；否则 `required` 抛错（**不等价于**顶层 system） | 原位 |
| user / assistant / tool | 正常映射 | 正常映射 |

> 是否需要特定 Beta Header，交由 `ProviderProfile` / Header Codec 的能力声明处理，不进入本层判定。

### 5.2.2 Privacy / Cache 的 system 迁移契约

| 依赖 | 现状 | 迁移契约 |
|---|---|---|
| `privacy/runtime.ts::injectSystemNotice` | 向 `canonical.system` 追加隐私提示 | 注入**首部 system 段**（首部连续 system/developer 消息末尾 text part）；不存在则新建首部 `system` 消息；保持「高权限、位于所有 user/assistant 之前」不变量 |
| `cache/anthropic/privacy-safe-cache.ts` | 按 `canonical.system` 提取 Anchor | Anchor 从**首部 system 段**派生，禁止扫描任意 system/developer 消息；保持 system→assistant→first-user 顺序 |

## 5.4 ContentPart 扩充

```ts
export type ContentPart =
  | TextPart | ImagePart | FilePart
  | ToolCallPart | ToolResultPart
  | ReasoningPart | RefusalPart
  | AnnotationPart
  | OpaqueNativePart;
```

- **`FilePart`**：本轮仅覆盖两协议能表达的文件形态；`openai-responses input_file` 为预留。
- **`RefusalPart`**：一等公共语义（唯一承载）。
- **`AnnotationPart`**：保留与文本内容的引用范围与原始 offset。
- **`OpaqueNativePart`**：未知块保留协议来源 + 原始内容，只能回到来源协议；跨协议 `required` 抛错（修 L-9）。
- `ReasoningPart` 拆分 `summary`（多 part）与 `text`。

## 5.5 Tool

- `ToolCallKind = "function" | "custom" | "provider"`。
- `namespace` 为正交命名维度。
- `ToolDefinition` 与 `ToolCall` 双 registry。
- **实施状态（§15.21）**：上述 registry 仍未落地。Anthropic server tool（`web_search_20250305`、`computer_20250124`、MCP connector 等）的**定义**以 `native.anthropic.{type,extra}` 承载（同协议保真、跨协议 `required` 报错）；其**调用/结果**仍按未知内容块走 `opaque_native`。Chat 侧只有 client-executed function tool。

## 5.6 字段所有权与 Native 来源不变量

**公共 IR 是可表达语义的唯一事实来源。**

- `native` 只承载公共 IR 无法表达的信息 + Presence/形态提示。
- **禁止双写**：`thinking.effort` 唯一（`outputConfig` 不含 `effort`）；`includeUsage` 唯一（`streamOptions` 不含 `include_usage`）；`refusal` 唯一（§5.1）。
- render 优先公共值。
- **Native 来源不变量（DEC-17）：**
  1. Parser **只填充来源协议分区**。
  2. 跨协议投影**不得隐式使用**其他分区的原生字段。
  3. 公共 API 接受外部构造的 IR 时，**校验一致性**（分区来源与声明格式匹配）。

### 5.6.1 Cache Metadata Accessor（DEC-14，修 L-14）

所有缓存断点访问必须经同一抽象：

```ts
function getCacheControl(part: ContentPart): CanonicalCacheControl | undefined {
  return part.native?.anthropic?.cacheControl;
}
```

Cache 与 Privacy **不得各自实现**缓存断点识别。涉及的三个模块（`privacy/request.ts`、`privacy/redact.ts`、`cache/anthropic/privacy-safe-cache.ts`）统一改用该 Accessor。

## 5.7 字段策略：类型绑定与三层覆盖

```ts
export interface FieldPolicyContext {
  sourceFormat: ApiFormat;
  targetFormat: ApiFormat;
  path: string;
  value: unknown;
}
export type FieldPolicy = DropPolicy | ((ctx: FieldPolicyContext) => DropPolicy);

export type PolicyFor<T> = {
  [K in keyof Required<T>]-?:
    | FieldPolicy
    | PolicyFor<NonNullable<T[K]>>;
};

const CHAT_REQUEST_POLICY = {
  n: ({ value }) => (typeof value === "number" && value > 1 ? "required" : "droppable"),
  responseFormat: "required",
  store: "required",
} satisfies PolicyFor<ChatNativeRequest>;
```

> 基础骨架；实现时需专门处理数组元素、union、`nullable`、`Record<string, unknown>`，不得照搬。

| 层级 | 规则 |
|---|---|
| 静态具名字段 | 编译期强制覆盖（`satisfies PolicyFor<T>`） |
| 动态字段 | 必须存在**显式 fallback policy** |
| 不可识别类型 | 按来源与安全规则决定保留 / 拒绝 / 显式丢弃 |

## 5.8 默认策略原则

| 类别 | 策略 | 例 |
|---|---|---|
| 内容/不可重建状态 | `required` | reasoning signature/encryptedContent、tool_call id、base64 image、file/document、refusal、opaque native、custom input |
| 决定输出结构 | `required` | `response_format`、`n>1`、`allowed_tools` |
| 数据保留/合规 | `required` | `store`（责任边界见 §5.10） |
| 路由/遥测/可选调参 | `droppable` | `service_tier`、`top_k`、`logprobs`、`top_logprobs` |
| 可重算结构 | `droppable` | Chat `created` |

## 5.9 覆盖、Unknown 与「能力 / 损失」分离

- **Provider 能力**（`ProviderProfile.capabilities`）：目标能否表达/转换。
- **Projection Policy**：调用方是否允许**字段丢弃**（独立于能力）。

约束：路径运行时校验；限定 source/target；不可覆盖硬集合禁止放宽；仅 `required → droppable`。

| 场景 | 默认 |
|---|---|
| 未知字段，同协议 | 保留（`extra`） |
| 未知字段，跨协议 | **报错** |
| 未知事件，同协议 | 尽可能保留语义与必要原生数据 |
| 未知事件，跨协议 | **报错** |
| 显式登记为可丢弃 | 允许丢弃并审计 |

## 5.10 数据保留责任边界

- `store` 标 `required`。
- Projection Planner **不**断言目标端数据保留政策；真正约束放到独立 **Provider 数据处理契约**。

# 6. Projection Planner

## 6.1 双向投影上下文（P0-1 / DEC-12）

请求与响应方向相反，必须显式建模：

```ts
export interface ProjectionContext {
  phase: "request" | "response" | "stream";
  inputFormat: ApiFormat;
  outputFormat: ApiFormat;
  inputProfile: ProviderProfile;
  outputProfile: ProviderProfile;
}
```

Pipeline 构造（`from`=客户端协议，`to`=上游协议）：

```ts
const requestContext  = { phase: "request",  inputFormat: from, outputFormat: to,
                          inputProfile: source.profile, outputProfile: target.profile };
const responseContext = { phase: "response", inputFormat: to,  outputFormat: from,
                          inputProfile: target.profile, outputProfile: source.profile };
```

`FieldPolicyContext` 由 `ProjectionContext` + `{ path, value }` 组成。**`DropRecord` 记录当前投影方向**（`sourceFormat=inputFormat`、`targetFormat=outputFormat`）。

## 6.2 保真四态与能力优先裁决

| 保真态 | 含义 | Planner 是否自动执行 |
|---|---|---|
| **Exact render** | 结构/语义直接对应 | ✅ |
| **Lossless transform** | 可证明语义等价 | ✅ |
| **Feature Adaptation（Lossy approximation）** | 用户**主动授权**的语义近似 | ❌ 需显式功能策略 |
| **Unsupported** | 目标无法表达 | 走 `applyPolicy` |

```text
if 语义等价表达:      Exact render
else if 语义等价转换: Lossless transform
else if 显式 Feature Adaptation 授权: 近似转换（非无损）
else:                applyPolicy(policy(f))   # droppable → drops；required → throw
```

### 6.2.1 Projection Policy 与 Feature Adaptation Policy（P1-2 修正）

- **Projection Policy**：字段能否**丢弃**。
- **Feature Adaptation Policy**：用户主动授权的**语义近似能力**（如 `cache_control → prompt_cache_key`）。

优先级规则：

1. Feature Adaptation **不是**普通字段保真裁决，**不覆盖** `required` 的「不得语义损失」约束。
2. 其产物必须记为 `transformed`，并记录语义损失诊断；**`Fidelity` 不得为 `EXACT`**（最低 `COMPATIBLE`，有损则 `LOSSY`）。
3. 未显式授权时，`required` 字段仍走 `applyPolicy`（抛错）。

**不变量：`required` 字段不得在无授权情况下发生语义损失。**

## 6.3 DropRecord

```ts
export interface DropRecord {
  phase: "request" | "response" | "stream";
  path: string;
  sourceFormat: ApiFormat;   // = 当前投影的 inputFormat
  targetFormat: ApiFormat;   // = 当前投影的 outputFormat
  reason: "unsupported_by_target" | "allowed_by_policy";
}
```

- 禁止记录原始值、完整 native 对象或含敏感信息的动态键名。
- 提交时机：每阶段结束聚合一次；流取消时提交已收集部分。

## 6.4 三阶段错误语义与失败层级

```ts
type TranslationFailurePhase = "parse" | "privacy" | "projection" | "render" | "upstream";
```

| 阶段 | 行为 |
|---|---|
| 请求投影（出站前） | 抛 `TranslationError{kind:"unsupported", code:"non_droppable_field", field}`；调用方边界决定 HTTP 映射 |
| 非流式响应投影 | 统一转源协议错误 Response |
| 流式响应投影 | renderer **之前**设安全裁决层；已输出内容后只能发**唯一**终止错误事件，或以明确 stream error 结束 |

要求：

- `StreamValidator` 自检错误与上游显式 `error` 走**同一终止路径**；terminal 后任何事件不得放行（修 L-6）。
- Trace/Completion 必须标明 `failurePhase`，并区分「已成功向客户端输出」与「仅内部记录」的事件。

## 6.5 Plan / Execute 分离与结算

非流式响应渲染两次（`translate.ts:371`、`:385`），Planner 不得随之重复执行：

```ts
const plan = planResponse(canonicalResponse, responseContext);  // 纯结构决策，计算一次
const observed = executePlan(plan, canonicalResponse);          // 隐私恢复前观察视图
restoreResponse(canonicalResponse, ...);
const final = executePlan(plan, canonicalResponse);             // 隐私恢复后最终视图
```

- `ProjectionPlan` 只含结构决策，不保存敏感字符串。
- `executePlan` 可重复调用且结果一致（除隐私恢复导致的变化）。
- `drops`/`failurePhase` 由 `planResponse` 阶段产生一次。
- **结算**：Planner 抛错时 `onComplete`（恰好一次、`errored`）、`trace`、`drops` 按「已发生」结算。

## 7.2 Usage 全局生命周期（P0-4 / DEC-15）

interface StreamState {

# 8. Privacy 与 Projection 契约

## 8.1 双轴证据模型

```ts
export interface FieldEvidence {
  path: string;
  privacy: "not_applicable" | "inspected" | "redacted" | "allowed" | "rejected";
  projection: "rendered" | "transformed" | "dropped" | "rejected";
}
```

## 8.2 不变量（fail-closed）

1. 所有可能到达 Provider 的字符串字段必须有明确 Privacy 覆盖策略。
2. 被丢弃字段无需转发，但必须有可信投影记录。
3. `rejected` 字段绝不能出现在最终请求中。
4. **Native 未知字段（含 `extra`）同样必须经过 Privacy 覆盖。**
5. `droppable` 只控制协议保真，**不代表隐私处理可跳过**。

## 8.3 Choices-aware Privacy Restore（P0-2）

```
for (const choice of response.choices) walk(choice.content);   // 非流式（修 L-12）
```

流式恢复缓冲与 `StreamBlockKey` 对齐，**不得**以裸 `index` 为键（修 L-13）：choice 0 与 choice 1 的同 `content` 索引互不干扰。

## 8.4 Cache Metadata 迁移（P0-3）

- 三处依赖统一改用 `getCacheControl()`（§5.6.1）。
- 回归测试：锚点顺序迁移前后不变；相同已脱敏输入的缓存键一致；跨缓存断点的隐私检测仍能拒绝；image/tool/tool_result 上的 `cache_control` 同样正确处理。

## 8.5 具体改造

- `collectRequestRegions`：遍历源从 `extensions` 改为 native 分区 + 公共字段全量。
- `verifyExtensions`：covered 字段要么「被安全处理且已转发」，要么「被可信投影记录为 dropped」。
- `verifyEgress` 保持最终出站校验职责。
- 未知 Native 动态键名无法登记时默认 `reject`（§4.4）。

function calculateFidelity(
  warnings: TranslationWarning[],
  drops: DropRecord[],

## 15.21 Anthropic server tool 定义（A 方案落地）

**缺陷（fix 前）**：Anthropic 请求里的 server tool 定义（例 `{ type: "web_search_20250305", name: "web_search", max_uses: 5 }`）被 `parseTools` 只读 `name`/`description`/`input_schema`，`type` 与类型专属参数静默丢弃；同协议往返退化为 `{ name, input_schema: {} }`，跨协议（→Chat）伪装成空的 client function tool，且**无 warning、无 drop 记录**（违反「无静默降级」与 docs/03 §15.1 的 server-side tools 边界）。

**修复**：

- `AnthropicNativeTool` 增 `type?: string`；`type !== "custom"` 的非空字符串即 server tool。`custom` 是 Anthropic 隐含默认，解析时归一化丢弃（语义等价，EXACT）。
- `parseTools`：server tool 的其余键（`max_uses`/`display_width_px`/残留 `input_schema` 等）逐字存入 `native.anthropic.extra`，canonical `inputSchema` 留空（不再合成假的 `{}` schema）；custom tool 的未知残留同样入 `extra`（同协议保留，§5.9）。
- Anthropic render：`native.anthropic.type` 存在时输出 `{ type, name, description?, ...extra, cache_control? }`，**不**输出 `input_schema`；否则维持原 custom 形态（`extra` 一并回写）。
- `ANTHROPIC_TOOL_POLICY` 增 `type: "required"`；新增 `projectAnthropicTool()`，Chat render 逐个 tool 裁决 → server tool 抛 `non_droppable_field`（`tools[i].native.anthropic.type`）。`cacheControl` 不在此重复裁决：Chat codec 已以 LOSSY `privacy_cache_control_dropped` warning 报告。
- Privacy：`collectNative` 支持路径前缀，tool 级 native（`tools[i].native.anthropic.*`）纳入 native 覆盖（默认 `allow` 入 haystack，`redact` 就地改写，`reject` 检测门控）；Anthropic render 对 `type`/`extra` 上报 disposition 以维持双证据。

**验证**：新增 `tests/anthropic-messages/server-tools.test.ts`（7 用例）覆盖 round-trip、cache 共存、`custom` 归一化、非字符串 `type` 校验、跨协议 fail-closed、custom tool 不回归、native `redact` 端到端。
