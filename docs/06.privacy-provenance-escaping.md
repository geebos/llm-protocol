# llm-protocol 隐私占位符来源隔离与可逆转义技术设计

**文档版本：** v1.0（implementation-freeze）
**日期：** 2026-10-13
**适用仓库：** `llm-protocol`
**范围：** 隐私层占位符命名空间隔离——来源感知的可逆转义（Provenance-aware Reversible Escaping）+ 有限状态转换器（FST）+ 占位符注册表（Token Registry）
**修订对象：** [`docs/04.privacy-transform.md`](04.privacy-transform.md) §6.4（碰撞）、§7.6（EgressVerify 未知形状）、§8.3（未知/不完整占位符）、附录 C（占位符语法与冲突规则）
**目标版本：** `2.x`（不破坏公开 `translate` 签名；新增 `mapping.escape` 配置与错误码）
**核心结论：** 把「外部字面量 vs 可信占位符」从**字符串形态判别**升级为**来源判别**。对可转义文本通道用可逆前缀转义消除歧义；对不可转义的结构字段显式拒绝。**SR-3 的绝对保证不可由纯文本算法达成**；本设计选择将 **llm-protocol 自身认定为可信引用通道**（仅本请求 Registry 登记的占位符可还原，已转义形状永不还原），并以此界定保证范围（§4 DR-1）。

> **需求来源：** 用户评审意见《占位符命名空间隔离》v1.0；本仓库现行 [`docs/04.privacy-transform.md`](04.privacy-transform.md) v1.6；Canonical IR / Stream 状态机；`src/privacy/*` 现有实现。
> **不变量继承：** 本文新增/修订 INV-E* 与 INV-*（docs/04 §11.2）并存，冲突处以本文为准并回写 docs/04。
> **安全硬约束：** 转义只作用于**确定为非隐私**的字面量；隐私原文与映射仍**禁止**进入 trace / report / 日志 / 错误消息。

# 1. 背景与问题陈述

## 1.1 问题

Agent 读取的**文件内容 / 用户输入 / 工具结果**中，可能本来就包含与隐私占位符**格式相同**的文本：

- **完整**：`<private_placeholder_phone_1>`；
- **形状相同但未登记**：`<private_placeholder_whatever_9>`；
- **带转义或截断**：`\<private_placeholder_phone_1>`、`<private_placeholder_phone_`。

现行实现（`src/privacy/redact.ts:274`、`src/privacy/restore.ts:74`、`src/privacy/stream.ts:191`、`src/privacy/egress.ts:96`）在**同请求存在 PII 时一致 fail-closed**：

| 现状 | 触发点 | 结果 |
| --- | --- | --- |
| 字面量等于将生成的占位符 | `redact.ts` `haystack.includes(mapping.placeholder)` | 拒绝 `privacy_placeholder_collision` |
| 字面量为未登记形状（入站 / 出站） | `egress.ts`、`restore.ts`、`stream.ts` | 拒绝或 warning `privacy_unknown_placeholder` |
| 原文等于已登记占位符 | `redact.ts` `session.lookupPlaceholder(original)` | 跳过 + `privacy_channel_skipped` |

由此产生两个结构性问题：

1. **双向误判**：合法的外部字面量既可能主动触发拒绝（存在碰撞），也可能因为形状扫描而触发未知占位符（不存在被登记）。即「**存在或不存在都会报错**」。
2. **来源不可判定**：纯字符串层面无法判断一个 `⟦P:...⟧` 形文本是**引擎生成的可信占位符**还是**外部输入的字面量**。碰撞检测只能拒绝，不能消歧。

> 这不是「字符串替换写得好不好」的问题，而是**可信占位符与外部字面量之间的命名空间隔离（namespace isolation）**问题。

## 1.2 根因

| 层 | 现状 | 缺失 |
| --- | --- | --- |
| 识别 | Detection 作用于原始文本 | 无「片段来源（provenance）」概念 |
| 替换 | 只替换命中区间，其余文本原样透传 | 未转义外部形状字面量 |
| 还原 | `restore` 只认已登记 Trie；未知形状原样 | 无法区分「外部字面量回显」与「占位符被改写」 |
| 校验 | EgressVerify 见未登记形状即拒 | 把合法字面量当威胁 |

# 2. 目标与非目标

## 2.1 目标

| 编号 | 目标 |
| --- | --- |
| PE-001 | 引入**来源感知**片段模型：`literal` / `privacy` / `trusted_token`，来源由可信流程决定，不由文本长相推断。 |
| PE-002 | 对确定为非隐私的**可转义字面量**执行**可逆前缀转义**，消除与占位符的形状歧义。 |
| PE-003 | 反向还原使用**单遍、非递归** FST，优先级：已转义 > 已登记 > 未登记形状 > 普通字符；**禁止二次解码**。 |
| PE-004 | 流式与非流式**复用同一解析器**，建立分块不变性 `F(x) = F(x₁,…,xₙ)`。 |
| PE-005 | Registry **精确匹配**已登记 token；未登记形状永不触发隐私还原。 |
| PE-006 | 字段级可转义策略（FR-4/CO-3/CR-4）：不可转义的结构字段出现形状冲突时显式拒绝。 |
| PE-007 | 消除 `privacy_placeholder_collision` 与「未知形状即拒绝」两类误判。 |
| PE-008 | 明确 SR-3 的**保证范围**，并提供「结构化引用通道」严格选项。 |

## 2.2 非目标

- 不改变识别结果与占位符模板语义（`{type}` / `{N}` / `{tag}`）。
- 不引入 Base64 / 全文编码等破坏可读性的方案。
- 不承诺「模型自由生成文本中的任意占位符都能被安全还原为原文」。
- 不处理多模态、跨进程持久化 Vault。
- 不改变 docs/04 已冻结的 streaming 生命周期不变量（INV-6）。

# 3. 需求映射与术语

本文引用外部需求条目，语义定义如下（以本文为准）：

| 条目 | 含义 |
| --- | --- |
| **SR-1** | 隐私识别必须作用于**原始文本**；转义不得改变识别输入。 |
| **SR-2** | 隐私优先于字面量保护；同一文本中隐私与字面量**互不污染**。 |
| **SR-3** | **只有本请求登记的可信占位符**才能触发敏感原文还原。 |
| **FR-4** | 字段级转义策略；不同通道可配置不同处理。 |
| **CO-3** | 结构化字段（工具调用 ID、JSON Key、路径标识）不得被文本转义破坏协议。 |
| **CR-4** | 无法保持来源隔离的输入必须**显式拒绝**，不得静默放行。 |

术语：

| 术语 | 定义 |
| --- | --- |
| **Provenance** | 片段来源，取值 `literal` / `privacy` / `trusted_token`；只能由可信流程赋值。 |
| **Shape（形状）** | 能被 `scanTemplateShape` 匹配的模板字面量，无论是否已登记。 |
| **Registered Token** | 当前请求 Registry 中登记、由本引擎生成的占位符。 |
| **Escapable Field** | 允许文本转义的通道（见 §11）。 |
| **Structural Field** | 不可改写的结构化字段（JSON Key、tool_call_id 等）。 |

# 4. 理论边界：SR-3 的可达性

**结论：仅凭最终输出字符串，无法在所有情况下判定一个形状文本来自「真实占位符」还是「外部字面量」。**

反例：外部字面量 `P` 与本次登记的真实占位符 `P` 完全相同。输入转义可以区分二者；但若模型主动去掉转义符，最终文本又完全相同。此时任何**只接收最终字符串**的确定性算法都无法区分来源。

因此：

| 方案 | 保证范围 | 代价 |
| --- | --- | --- |
| **A. 工程化（本文默认）** | 保证**遵循转义协议**的文本：`D(E(x)) = x`，已转义形状永不触发还原；未转义且已登记者才还原 | 模型破坏转义协议时可被诱导还原 |
| **B. 严格来源保证** | 敏感原文**只能**经可信程序管理的**结构化引用通道**还原，模型自由文本中的 token 一律不触发 | 破坏「文本内联引用即还原」的可用性 |

> **设计决策（DR-1）：已关闭（2026-10-13）。** 采用方案 A，并将 **llm-protocol 自身认定为可信引用通道**：只有当前请求 Registry 登记的占位符（Registry-based Exact Match）才触发还原，已转义形状永不还原。因此 `mapping.restorePolicy: "structured_only"` 不在计划内；SR-3 的保证范围即「遵循转义协议、且 token 由本请求 Registry 登记的文本」。若未来要求「模型自由文本 token 一律不还原」，再另行引入方案 B。

# 5. 总体设计

```text
                    原始模型可见文本（未转义、未替换）
                                 │
                        ① 隐私识别（作用于原始文本，SR-1）
                                 │
        ┌────────────────────────┴────────────────────────┐
        │ privacy 片段                                     │ literal 片段
        ▼                                                  ▼
 ② 生成可信占位符并登记 Registry              ③ 仅对 shape 字面量做前缀转义
        │                                                  │
        └────────────────────┬─────────────────────────────┘
                             ▼
                  ④ 序列化为模型可见文本
                             │
                             ▼
                     —— 上游模型 ——
                             │
                    ⑤ 单遍 FST 解析与还原
                   （已转义 > 已登记 > 未知形状 > 普通）
                             │
                    ⑥ 独立外发校验（EgressVerify）
                             │
                             ▼
                       客户端可见输出
```

推荐算法组合：

| 组件 | 机制 | 解决的问题 |
| --- | --- | --- |
| 来源区分 | Provenance-aware Segment | 区分系统生成占位符与外部字面量 |
| 字面量保护 | Reversible Escaping（前缀转义） | 避免外部文本被误认为隐私占位符 |
| 流式处理 | FST / DFA + 有界缓冲 | 跨 Chunk 识别、确定性处理、分块不变性 |
| 多占位符匹配 | Trie（默认）/ Aho–Corasick（大 Registry） | 高效识别已登记 token |
| 安全还原 | Registry-based Exact Match | 只还原当前请求登记的占位符 |
| 防伪与稳定 | HMAC 派生标识（长度前缀编码） | 降低碰撞与字典猜测，同时保证确定性 |
| 最终校验 | Independent Egress Validator | 防止隐私绕过与异常输出 |

> **DR-2：** 不单独采用「正则替换 / Base64 全文编码 / 纯随机 Token」。它们分别导致来源歧义、可读性受损、缓存不稳定。

# 6. 领域模型：带来源的文本片段

**不要直接对所有文本做正则替换。** 先在内部把文本切成带来源属性的片段：

```ts
export type Segment =
  | { kind: "literal"; text: string }
  | { kind: "privacy"; start: number; end: number; entityType: string; value: string }
  | { kind: "trusted_token"; tokenId: string; placeholder: string };
```

- `kind` **必须由可信处理流程赋值**，禁止从文本长相推断。
- `privacy` 片段携带原始区间与识别类型，供 Registry 分配使用。
- `trusted_token` 片段由 `PseudonymAllocator` 产出，不允许再次转义。

## 6.1 处理顺序（与 SR-1/SR-2 对齐）

```text
1. 在原始文本上运行 recognizer（隐私优先，SR-1）
2. Span 裁决（沿用 docs/04 §6.2）
3. 对 privacy 片段分配/复用占位符（Registry）
4. 对剩余 literal 片段执行 shape 转义（§7）
5. 序列化 → 模型可见文本
```

这样：**转义不改变隐私检测的输入**，且隐私片段与字面量片段互不污染（SR-2）。

> **与现行实现的差异：** 现行 `redactRegions` 只替换 detection 区间，其余文本原样透传，因此需要额外增加步骤 4，且步骤 4 必须**跳过** `trusted_token` 区间。

# 7. 可逆转义（Escape / Decode）

## 7.1 保留字符

- 转义字符：`\`（U+005C）。
- 模板编译已**禁止**字面量包含 `\`（`template.ts` `FORBIDDEN_LITERAL`），因此生成占位符**保证不含转义字符**（INV-E2）。
- shape 起始字符：`compiled prefix[0]`（默认模板即 `<`）。

## 7.2 编码 `E`

对 literal 文本 `x`：

```text
E(x)：
  单遍扫描
  遇到 `\`                → 输出 `\\`
  遇到 shape 的起始位置    → 在 shape 前插入 `\`（仅插入一次，其余字符原样复制）
  其它                    → 原样输出
```

示例（模板 `<private_placeholder_{type}_{N}>`）：

| 外部原始文本 | 模型可见文本 | 最终还原 |
| --- | --- | --- |
| `<private_placeholder_phone_1>` | `\<private_placeholder_phone_1>` | `<private_placeholder_phone_1>` |
| `\<private_placeholder_phone_1>` | `\\<private_placeholder_phone_1>` → 再转义起始 `<` 得 `\\\<private_placeholder_phone_1>` | `\<private_placeholder_phone_1>` |
| `a\b` | `a\\b` | `a\b` |
| `hello` | `hello` | `hello` |
| `<not a shape>` | `<not a shape>`（无闭合，非 shape） | `<not a shape>` |

> 现行文档示例使用 `⟦P:ABC123⟧`，本仓库默认模板为 `<...>`；转义规则与符号无关。

## 7.3 解码 `D`

```text
D(y)：单遍、非递归
  遇到 `\` 且下一个字符是 `\`            → 输出 `\`，前进 2
  遇到 `\` 且下一个字符是 prefix[0]      → 输出该字符，前进 2，并进入「字面量」状态
                                          （后续 shape 剩余字符按普通文本复制，不再参与匹配）
  遇到 `\` 且下一个字符不是以上任一       → 输出 `\`，前进 1（防御性）
  其它                                   → 原样输出
```

**关键：不能先去掉所有反斜杠，再执行一次普通占位符替换**，否则误还原问题重新出现。

## 7.4 可逆性

对任意 literal 文本 `x`：

```text
D(E(x)) = x
```

`E` 为字面量编码，`D` 为对应的字面量解码。该等式保证**确定性编解码器**的可逆性，**不保证**模型自由生成的文本一定保持转义格式。

> **DR-3：** 若未来模板允许字面量包含 `\`，必须改用非模板字符作为保留字符，或把 `\` 一并纳入模板编译的转义体系。

# 8. 反向还原：单遍 FST

## 8.1 优先级

在模型输出 `y` 上，从左到右对每个位置按以下**严格优先级**分派：

| 优先级 | 条件 | 动作 |
| --- | --- | --- |
| 1 | `\` + prefix[0]（已转义形状） | 输出字面量 `prefix[0]`，前进 2；**禁止隐私还原** |
| 2 | 匹配 Registry 中的已登记占位符（Maximal Munch） | 还原为原文 |
| 3 | 匹配未登记 shape | 原样输出（可计数 + warning） |
| 4 | 其它 | 输出单字符，前进 1 |

- 单遍、非递归；**不二次解码**（INV-E3）。
- 已登记匹配沿用 docs/04 §9.2 的 Maximal Munch（前缀重叠，如 `..._1` vs `..._10`）。
- 未登记 shape 与已登记匹配器**共享安全输出边界**（docs/04 INV-17）：
  `SafeEmitBoundary = min(RegisteredMatcher.safeEnd, EscapeAwareBoundary.safeEnd)`。

## 8.2 边界与失败

| 情形 | 动作 |
| --- | --- |
| 已转义形状回显 | 还原为字面量，**绝不**触发占位符还原（INV-E7） |
| 未转义且已登记 | 按授权策略还原 |
| 未登记形状 | 保持字面量，计数 `unknown` |
| 前缀但流未结束 | 缓存等待 |
| 超 `maxPlaceholderLength` 未闭合 | 原样输出并重置 |
| 声称遵循转义协议但格式非法 | 明确失败并告警（不猜测） |

# 9. 流式处理：DFA + Trie

## 9.1 为什么不能用逐 Chunk 正则

```text
Chunk 1: "<private_placeholder_"
Chunk 2: "phone"
Chunk 3: "_1>"
```

独立处理每个 chunk 永远无法识别完整占位符。必须实现统一的增量解析器：

```ts
export interface TokenStreamDecoder {
  /** 输入 chunk，返回可安全释放的输出（可能为空）。 */
  feed(chunk: string): string;
  /** 流结束，处理剩余缓冲。 */
  flush(): string;
}
```

内部采用**带缓冲的状态机**，保留未完成前缀，仅在匹配明确后输出。

## 9.2 分层算法选择

| 情况 | 推荐 |
| --- | --- |
| 占位符格式固定、数量少 | DFA + 有界缓冲 |
| 需要精确匹配 Registry 中的 token | Trie |
| Registry 含大量不同 token | Aho–Corasick |
| 字面量格式由复杂规则定义 | 有界正则自动机 + Trie |

> **DR-4：** 不必一开始就上 Aho–Corasick。本仓库按请求维护 Registry，规模通常为个位到几十条；**默认 Trie + DFA** 更易验证正确性，`Registry.size()` 超过配置阈值（建议 `acThreshold = 256`）再切换 AC。

## 9.3 与非流式复用

非流式只是一次性把完整文本送入 `feed()`，最后调用 `flush()`。建立**分块不变性**：

```text
F(x) = F(x₁, x₂, …, xₙ)
```

右侧表示在同一状态机中依次输入所有分块并完成 flush，**不是**对各分块分别处理后拼接。

## 9.4 缓冲与安全

- 限制 `maxPlaceholderLength`（现行 128）、`maxTextPendingBytes`（现行 4096）、`maxToolArgumentBytes`（现行 1 MiB）。
- 超限按 `overflowAction`；`strict` 下恒 `reject`（继承 docs/04 §5.2）。
- 最终 Egress 校验必须在流式输出释放前执行；若校验需要整段上下文，必须缓冲到能完成校验为止。
- `escape` 状态同样受缓冲上限约束，禁止无限等待未闭合转义。

# 10. Token Registry 与稳定标识

## 10.1 数据结构

```ts
export interface TokenRecord {
  id: string;
  token: string;        // 模型可见占位符
  original: string;     // 隐私原文（敏感，禁止外泄）
  entityType: string;
}

export type TokenRegistry = Map<string, TokenRecord>;   // token -> record
```

Registry **只保存精确映射**，还原**不**通过占位符正则推断。Registry 请求级存活，跨请求输出还原必须从当前请求的可信输入重建映射（继承 docs/04 §10.1）。

## 10.2 稳定标识

**选项 A：顺序编号（默认，现行）**

```text
n = counters[type] + 1
placeholder = render(template, type, n, tag?)
while placeholderToReal.has(placeholder): n++
```

- 按 IR 文档顺序串行分配（docs/04 PR-009/PR-018），保障 prompt cache 前缀稳定（PT-26）。
- 同请求内 `(type, original)` 恒定映射（INV-7）。

**选项 B：HMAC 派生标识（opt-in）**

```text
ID = Trunc₁₂₈( HMAC_K( ContextID ∥ Type ∥ Value ) )
```

- `∥` 必须是**无歧义的长度前缀编码**，禁止简单字符串拼接。
- 好处：相同上下文/相同隐私值生成相同占位符，跨请求缓存更稳；降低普通无密钥哈希的字典猜测风险。
- 约束：`ContextID` 必须在需要复用缓存的上下文中**保持稳定**；**禁止**用完整请求内容哈希作为前缀命名空间，否则追加一条消息会导致历史占位符全部变化。
- 与模板兼容：把 `ID` 映射为模板 `{N}` 分支（推荐）或作为 `{tag}` 使用；发生会话内碰撞时递增探测。

```ts
export interface PrivacyMappingOptions {
  template?: string;
  tagMode?: boolean;
  tagBytes?: number;
  /** 新增：字面量转义开关（默认 true）。 */
  escape?: boolean;                              // 默认 true
  // restorePolicy 不在计划内：llm-protocol 自身即可信引用通道（§4 DR-1）
  idMode?: "sequence" | "derived";               // 默认 "sequence"
  tagContextId?: string;                         // derived 模式必填，需稳定
}
```

> 现行 `tagMode` 的 HMAC tag（`llm-protocol-privacy-v1` 域，≥96-bit）保持冻结；`idMode: "derived"` 复用同一密钥与域构造。

# 11. 字段级策略与保护区

## 11.1 通道分类

| 类别 | 通道 | 转义 |
| --- | --- | --- |
| **Escapable** | `system`、`message_text`、`tool_result`、`tool_description`、`tool_schema.text`、`tool_arguments`（JSON Value）、`extensions`（text 路径） | ✅ |
| **Structural** | JSON Key、`tool_call_id`、路径标识、`tool_schema.structural`、`tool_schema.valueBearing` 的键名 | ❌ |
| **Opaque** | `signature`、`encrypted_content`、`image`、`reasoning` | ❌（detect-only；reasoning 另不参与碰撞扫描） |

## 11.2 规则（FR-4 / CO-3 / CR-4）

1. Structural / Opaque 字段**不应用文本转义**，其来源信息保留在结构化对象中。
2. 若 Structural 字段出现 shape 字面量，且该字段必须原样暴露给模型、又无法保持来源隔离 → **显式拒绝** `privacy_field_unescapable`（CR-4），**不得静默放行**。
3. 若 Structural 字段的某个字符串是已登记占位符，且会破坏协议（如 JSON Key）→ 拒绝或保留 + warning（沿用 docs/04 `privacy_json_key_placeholder` 的语义，但不再依赖形状猜测）。
4. `tool_arguments` 继续 Value-only（docs/04 §7.3/§8.4）：Key 不转义、不还原。
5. `reasoning` 继续 detect-only：命中即拒绝（`privacy_signature_guard`），未命中透传。
6. **`reasoning` 不参与碰撞扫描**（`Region.collisionScan = false`），其文本也不参与 EgressVerify 的**外来形状**检查（`exemptTexts`）：其内容是模型生成、签名保护、且从不还原；其中的同形 token 是**合法引用**（多轮 extended thinking 回放）。原始 PII 仍由 detect-only 识别与 egress 原文比对拦下。
7. **引擎注入的 system 提示词同样从外来形状检查中豁免**：它是可信配置，可能自然包含占位符**示例**（如 `<private_placeholder_example_1>`）；默认 `{template}` 不属于形状，但自定义示例会。豁免仅限形状检查，原文比对仍生效。

## 11.3 保护区

- 保护区**仅限已有 `trusted_token` 片段**（已登记占位符）。
- 未登记形状字面量：在 Escapable 字段按 `literal` 转义；在 Structural 字段按 §11.2 拒绝。
- 转义文本不参与隐私识别、不参与碰撞扫描（因为转义后已是确定字面量），并计入 `escaped` 计数。

# 12. 外发校验（EgressVerify 修订）

`EgressVerify` 仍在所有 Payload 修改之后、`execute()` 之前运行，但语义修订为：

```text
EgressVerify(finalPayload):
  1. 标记【引擎生成的占位符】区间（Registry 精确匹配），从扫描文本中剔除（避免原文命中占位符子串，PT-65）
  2. 预计算 allowedOriginals（allow 通道出现的已识别原文；仅 policy 档）
  3. 扫描 String Value 与 Key：
       - 命中已识别 original：policy 且 ∈ allow → 跳过；否则拒绝
       - 出现【未登记且未转义】的 shape 字面量：
           · Escapable 字段 → 拒绝（转义不变量被破坏，说明有路径绕过 E）
           · Structural 字段 → privacy_field_unescapable
  4. 校验所有 Escapable 字段满足「无非转义 shape」（转义不变量兜底）
  5. 短值：默认出现即拒绝；minEgressValueLength 设下限
```

档位保持 docs/04 §7.6：

| `egress` | 语义 |
| --- | --- |
| `"policy"`（默认） | 尊重 `allow`；仅拦截其它位置的残留 |
| `"strict"` | 显式覆盖 allow：任意已识别原文出现即拒绝 |

> 与现行实现的差异：现行「未登记形状 = 立即拒绝」改为「**未登记且未转义**才拒绝」。合法转义字面量不再误报。

## 12.1 失败诊断（脱敏）

`privacy_uncovered_channel` / `privacy_unknown_placeholder` 失败时，错误消息列出**结构路径**与**星号脱敏后**的值，便于排障：

```text
A privacy-identified value survived into the outbound payload at metadata.note (phone: 1*********0); messages[0].content[0].text (phone: 1*********0)
```

- 位置：目标 Payload 内的路径；数组用 `[i]`，Key 自身用 `{key#i}`（不内嵌 Key 名，避免 Key 即隐私时泄露）。
- 内容：`maskValue` 仅保留首尾字符（长度 ≤ 2 全星号）；**原文永不出现**。
- 路径若恰好包含某个已识别原文，会先对该原文做同样脱敏（`sanitizePath`）。
- 一次失败最多列 `MAX_EGRESS_LEAKS = 10` 个位置，其余折叠为 `+N more`。
- 脱敏值仅出现在错误 `message`，不进入 trace / report / `cause`。
- `exemptTexts`（reasoning 段文本 + 注入的 system 提示词）跳过**外来形状**检查，但**原文比对仍生效**（reasoning 里的原始 PII 仍会被拦）。

# 附录 A：转义语法与规则

```text
literal      := { char }                        // 任意字面量文本
escape       := "\"                             // 保留字符 U+005C
escapedShape := "\" shape                        // 前缀转义（仅一个反斜杠）
shape        := 由 compiled template 实例化的模板形状（含 {type}{N}，tagMode 含 {tag}）
```

编码规则：

1. 先处理 `\`：每个 `\` 变为 `\\`。
2. 再处理 shape 起始：在每个 shape 的起始字符前插入一个 `\`；插入的反斜杠**不**参与步骤 1 的加倍。
3. 生成占位符（`trusted_token`）**不**参与转义。

解码规则：

1. 单遍、非递归。
2. `\\` → `\`。
3. `\<prefix[0]>` → `<prefix[0]>`，且该 shape 剩余部分按普通文本复制，不参与已登记匹配。
4. 其它 `\` 原样保留（防御性）。

| `privacy_escaped_literal` | info | literal 片段被转义（计数） |
| `privacy_escape_overflow` | reject/warning | 转义状态缓冲超限 |

# 附录 C：算法选择与性能

| 环节 | 复杂度 | 说明 |
| --- | --- | --- |
| `E` / `D` | O(n) | 单遍字符扫描，无回溯 |
| 已登记还原 | O(n · L)（Trie，L 为最长 token 长度） | 有界缓冲 |
| 还原 hold 点扫描 | O(W) per restore（W = `maxPlaceholderLength`） | 只与缓冲区尾部有关，每次恢复算一次；旧实现逐字符全缓冲回扫为 O(n²) |
| 大 Registry AC | O(n + matches) | Registry > `acThreshold`（建议 256）切换 |
| HMAC 派生 ID | O(1) per value（SHA-256） | 需稳定密钥与 ContextID |
| 内存 | O(Registry + buffer) | 缓冲受 `maxTextPendingBytes` / `maxPlaceholderLength` 约束 |

> 真正应优先确定的**不是** Aho–Corasick 还是 KMP，而是「**是否允许模型自由生成文本中的形状直接触发敏感原文还原**」。该决定关系 SR-3 能否被严格满足，也决定整个算法的安全边界（§4 DR-1，已关闭：llm-protocol 自身为可信引用通道）。
